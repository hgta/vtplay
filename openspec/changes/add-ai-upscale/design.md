## Context

本变更建立在 `add-film-restore-export` 建立的**阶段化流水线**之上，只增加一个阶段。
如果那套骨架先落地，这里的接入成本很小；若没有它，则必须先重构（这正是当时选阶段化而非单条滤镜链的原因）。

**已实测的环境事实**：

| 事实 | 含义 |
|---|---|
| 随包 ffmpeg **不含** `sr` 滤镜，也**不含**任何 DNN 滤镜 | 超分**必须**依赖外部工具 ✗ |
| ffmpeg 内的放大算法只有 `xbr` `hqx` `epx` `super2xsai` 等像素画算法 | 用于实拍老片会油画化，不能替代超分 ✗ |
| 本机 `libplacebo`（Vulkan）实测失败：`No memory type found for flags 0x2` | **Vulkan 能力不能假设**，必须实测 ✓ |
| 本机 QSV 可用：`[D3D11VA] Using device 8086:46a6 (Iris Xe)` | GPU 并非全然不可用，但不同路径结果不同 → 只信实测 |
| 本机为 Intel Iris Xe（核显，无独显） | 本机会落在 T1，但**这不能决定软件的能力上限** |

**核心设计立场**（用户明确要求）：软件的能力上限由**打开它的那台机器**决定，而不是开发机的条件。
因此本变更的重心是「**探测**」，而不是「按本机构建一个够用的实现」。

## Goals / Non-Goals

**Goals:**

- 任何机器都能用到**它在合理时间内能承受的** AI 超分，而不是二元地"支持 / 不支持"
- 耗时预估**在任何机器上都诚实**——用实测吞吐，不用型号查表
- 失败发生在**开始之前**，而不是等了 40 分钟之后
- 作为流水线的一个阶段接入，不重构既有结构
- 对 AI 放大的**性质**（生成 vs 还原）诚实标注

**Non-Goals:**

- 自研推理 / 把 ncnn 变成应用依赖 —— 与既有「不链接编码 API、以子进程隔离」的取向冲突
- 时序一致的超分模型（BasicVSR++ 等）—— 见 D8，v1 接受逐帧闪烁
- 人脸专修（GFPGAN / CodeFormer 类）—— 对老片有价值，但属于独立能力，另立变更
- 批量队列、多 GPU 并行、云端超分
- 训练或微调模型

## Decisions

### D1：外部工具 + 进程隔离，与既有 ffmpeg 做法一致

| | A. 自研推理（集成 ncnn） | **B. 外部工具（选定）** |
|---|---|---|
| 性能 | 最优，可流式 | 多一次 IO 往返 |
| 可分发性 | 需要把 ncnn 作为构建依赖 ✗ | 独立可执行文件，可随包可外置 ✓ |
| 与既有取向 | 冲突（应用本不链接编码 API） | 一致 ✓ |
| 替换后端 | 需要重新编译 | 换一个 exe ✓ |
| 许可 | 需引入更多依赖 | 运行时与模型许可独立、清晰 ✓ |

选定 B。核心理由是与项目既有架构取向一致，以及后端可替换（D9）。

### D2：帧序落盘是唯一可行的中继方式，磁盘是主要代价

```
理想的流式连接（不可用 ✗）
  ffmpeg ──rawvideo 管道──▶ 超分 ──rawvideo 管道──▶ ffmpeg
  问题：图像型超分工具只接受「图片文件或目录」，不支持 stdin/stdout 裸帧 ✗

实际采用（帧序中继）
  ffmpeg ──PNG 序列──▶ 超分工具（目录输入/输出）──PNG 序列──▶ ffmpeg
  · 优势：兼容任何图像工具；PNG 无损，质量只在最终编码时损失一次
  · 代价：1080p 约 2~4 MB/帧 → 3600 帧约 7~14 GB ✗✗
```

磁盘对策的取舍：

| 方案 | 峰值磁盘 | 复杂度 |
|---|---|---|
| **整段（v1 选定）** | 7~14 GB ✗ | 低 ✓ |
| 分块（每 N 帧一批，处理完立即编码并删帧） | ~1 GB ✓ | 中高（分段边界的 GOP 处理、进度拼接、重试粒度） |

v1 选整段，但**必须**在 preflight 中强制校验临时空间，并依赖「只处理选中时间段」把任务规模
控制在可行范围。分块列入后续（处理整部影片时才需要）。

### D3：能力探测以实测为准，型号只用于展示

```
探测流程:
  ① 枚举图形设备（厂商/型号/显存/独显判定）
  ② 验证超分运行时（执行一张极小测试图，超时判定失败）
  ③ 实测吞吐（处理固定小素材，量出帧/秒）      ← 预估值只信这个
  ④ 判定档位 T0~T3 + 记录判定依据
  ⑤ 按「设备标识 + 驱动版本」缓存
```

**不靠型号查表**的理由是硬性的：型号表无法覆盖未见于表中的设备，而那些机器上的预估会错得离谱 ✗。
实测慢一点（数十秒），但**在每台机器上都对** ✓

**指纹必须包含驱动版本**：本机的 `libplacebo` 失败就是一个「驱动行为」问题——
同一块 GPU 换个驱动版本，Vulkan 路径的可用性可能完全不同 ✓ 因此驱动变化必须触发重测 ✓
（这也是之前「换了转码器还显示旧版本」教训的同类问题：缓存键必须包含所有会改变结论的因素。）

### D4：档位表达「能承诺什么」，而不是「能不能用」

核显也能跑超分，只是慢 ✗ 二元判断会错误地关闭这个能力 ✓ 因此档位映射到三件事：

```
  T0 ──▶ 不提供 AI 放大（回退传统放大 + 说明原因）
  T1 ──▶ 提供，给出「建议片段长度」+ 强制展示 ETA
  T2 ──▶ 提供，中长片段
  T3 ──▶ 提供，长视频
```

档位同时携带**判定依据**（"集成显卡，实测 1.2 帧/秒"）✓ 可解释性对排查至关重要——
用户报"为什么我的机器不支持"时，答案应该是具体的一句话，而不是"不支持" ✗

### D5：preflight 必须在开始前完成全部检查

40 分钟后失败是不可接受的体验 ✗。检查顺序按**成本从低到高**：

```
  1. 档位是否 ≥ T1                （读缓存，零成本）
  2. 运行时是否可执行              （复用探测结果；失效才重验）
  3. 输出目录空间
  4. 临时目录空间（含帧序）        ← 需要先知道帧数：时长 × 帧率 × 单帧估算
  5. 预计耗时 > 阈值 → 明确预警 + 等待确认
```

### D6：超分后用高质量缩放收尾到目标分辨率

超分模型的放大倍数通常是**固定的**（常见 4 倍）✗，而用户目标往往是 2 倍 ✓

```
  720×576 源 ──(x4 模型)──▶ 2880×2304 ──(lanczos 缩小)──▶ 1440×1152
                                              ↑
                              副作用是好的：缩小会压掉超分引入的部分伪影
```

因此阶段顺序中，超分之后必然跟一个「收尾缩放」；目标是原尺寸时应跳过整个放大路径 ✓
若用户的目标倍数**超过**模型能力，必须在开始前拒绝（不能悄悄做不到）。

### D7：随包只带必要模型

模型是**分内容**的，用错模型比不用更差 ✗（动漫模型处理真人会塑料化，通用模型处理动漫会糊掉线条）：

| 模型 | 随包 | 理由 |
|---|---|---|
| 通用实拍模型 | ✓ | **老片主力** |
| 轻量视频模型 | ✓（体积很小） | 快 3~10 倍，用于预览与短片 |
| 去隔行 NN 权重 | ✓（约 1MB） | 提升去隔行质量（供 `add-film-restore-export` 使用） |
| 动漫专用模型 | ✗ | 老片用不到；带上是纯粹的体积浪费 |

体积影响：发布包约 103MB → **195~215MB**。若需要瘦身，可改为从本项目 Release 资产按需下载
（CI 已具备发布资产的能力），无需外部服务器 ✓ 但 v1 先随包，换取"开箱可用、无网络依赖" ✓

### D8：v1 接受逐帧超分的时间闪烁，并如实说明

逐帧独立推理的固有问题：相邻帧的"猜测"不完全一致 → 画面出现细微的**沸腾/抖动** ✗

- 时序一致的模型（BasicVSR++ 等）能缓解，但重量级、且需要视频级输入，与帧序中继不兼容 ✗
- v1 的缓解手段：超分前的轻降噪（减少高频不一致的来源）+ 超分后的收尾缩放（压掉部分伪影）
- **不假装没有**：这是已知代价，写入界面说明；时序模型列入后续

### D9：后端可替换

v1 只实现 `ncnn-vulkan`（通用：NV / AMD / Intel 都能跑）✓
接口预留，使 NVIDIA 机器将来可换用 TensorRT/CUDA 后端（快 2~5 倍）✓
这与 `ffmpeg` 的后端无关，属于超分阶段自身的抽象 ✓

### D10：帧序命名与编号的校验（逐帧处理最经典的错误来源）

```
ffmpeg 输出：  frame_%08d.png   → 从 00000001 开始
超分输出：      必须保持相同编号与数量

校验：① 输入帧数 == 输出帧数            ② 编号连续无缺
      ③ 任一不满足 → 拒绝继续（不能产出一段静默错位的视频）✗
```

这条校验是纯客观、零成本的强门禁 ✓ 规格中已断言 ✓

### D11：明确「马赛克」的两类边界

区分是针对**用户预期**的诚实设计，不是文字游戏：

| 类型 | 特征 | 本能力的态度 |
|---|---|---|
| **压缩块效应** | 块大小随码率变化、边界不对齐网格、伴随蚊噪 | **可改善** ✓ 属于修复范畴 |
| **人为打码** | 块大小固定且整齐、边界严格对齐网格、无其他伪影 | **信息已销毁，不可还原** ✗ |

后者在数学上是多对一映射（把 N×N 像素替换为其均值），**逆函数不存在**；
任何"看起来还原了"的结果都是**生成**的，不是**还原**的。

因此本能力 MUST NOT 承诺"去除打码" ✓ 界面按 D12 如实标注 ✓

### D12：对 AI 放大的性质如实标注

界面 SHALL 说明：AI 放大生成的是**合理的细节**，输出与真实原貌存在差异 ✓
这条必须在**选择该功能时可见**，而不是藏在文档里 ✓

## Risks / Trade-offs

- **[核显机器上极慢]**（本机 T1，2 分钟视频可能数十分钟至数小时）→ 档位 + 实测 ETA + 片段长度建议 + preflight 预警；**必须**配合「只处理选中时间段」
- **[帧序占用磁盘巨大]**（1080p 可达 7~14 GB）→ preflight 强制校验临时空间；时间段限制规模；分块处理列后续
- **[逐帧超分的时间闪烁]** → 已知代价（D8）：轻降噪前置 + 收尾缩放缓解 + 如实说明
- **[Vulkan/驱动行为差异]**（本机 `libplacebo` 已实测失败）→ 运行时实测验证（D3）+ 指纹含驱动版本 + 失败降级为 T0（不伪装可用）
- **[模型产出"很像但不是它"]** → 明确标注（D12）+ 不承诺"还原"（D11）
- **[发布包体积翻倍]** → 只带必要模型（D7）；可拆为按需下载
- **[帧序缺帧导致画面静默错位]** → 帧数与编号校验，不满足即拒绝继续（D10）
- **[模型权重的许可是独立问题]**（运行时 BSD-3，但权重各有条款）→ 逐个确认并写入「关于」页；如实标注来源
- **[探测本身耗时的打扰]**（数十秒）→ 后台执行 + 缓存 + 界面保持响应

## Migration Plan

1. **能力探测**：设备枚举 + 运行时探针 + 实测吞吐 + 档位 + 缓存（可独立验证，不依赖导出改动）
2. **超分阶段执行**：帧序中继 + 帧数/编号校验 + 收尾缩放 + 取消与清理
3. **preflight 接入**：按 D5 的顺序接入，并把帧序空间需求计入既有空间校验
4. **界面**：档位与判定依据、实测 ETA 与片段建议、模型选择、诚实标注
5. **随包**：打包脚本与 CI 携带运行时与模型；「关于」页补许可与来源
6. **回归**：`add-film-restore-export` 的经典路径行为不变；T0 机器上回退行为正确

**回滚**：AI 超分是流水线的一个可选阶段，回滚只需移除该阶段与随包内容，
不影响经典修复路径（阶段化骨架的其他阶段照常工作）。

## Open Questions

- 探测用固定测试素材的尺寸与内容如何选取，以在「探针耗时」与「吞吐代表性」之间取得平衡
- 档位到「建议片段长度」的具体阈值需实测标定（不同档位的可接受等待时间不同）
- 是否需要分块处理以支持整部影片（关系到「能不能处理长片」这个产品问题）
- 模型权重的许可确认结果（需逐个确认后写入「关于」页）
- 是否引入时序一致模型以消除闪烁——取决于实际观感能否被用户接受
