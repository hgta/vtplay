# Proposal: 解码背压——暂停时保证「显示位置之后的 N 帧」可用

## Why

逐帧步进虽已可用且帧级精确，但**前进/后退每步都要回关键帧重解**（实测 76 / 166 ms，
4K60 HEVC）。原因不是解码慢——用轻 60 倍的 1080p 素材实测延迟几乎相同，
瓶颈是 seek 握手（详见 `add-ui-shell/tasks.md` 6g.9）。

其中**前进本可零成本**：帧队列里就有后续帧，只要把时钟推一格、渲染层下一拍就能显示。
但它拿不到——`FrameQueue` 的视频侧是「超出容量丢最旧」（`videoCapacity_`），
而解码线程在暂停时并不停，于是「紧跟显示位置的那几帧」会被后来的帧挤掉。
实测连续前进两步后就取不到帧了。

## What Changes

给视频帧队列引入**保留窗口**概念，并据此对解码施加背压：

- 渲染层每取到一帧，就在队列上更新「保留窗口」：**该帧之后 N 帧不得被丢弃**
- 推帧时若「窗口之外的帧数」已达容量，**阻塞生产者**（而不是丢窗口内的帧）
- 于是暂停时：显示位置之后的 N 帧一定在缓冲里 → 前进零成本；
  同时解码不再空转（暂停时它不再一路解码再被丢掉，省 CPU）

## Impact

- `FrameQueue`：新增保留窗口与阻塞式推入；视频推入从「丢最旧」变为「窗口内保护 + 窗口外阻塞」
- `MediaPipeline`：渲染/取帧路径更新窗口基点；seek 无需特殊处理
- `VideoRenderer` / 取帧口径不变
- 预期收益：逐帧前进从 ~76 ms 降到**一帧 tick 量级**（约 30 ms），后退不受影响

## Non-Goals

- 不改后退路径（没有帧历史缓冲的前提下，回关键帧重解是必需的）
- 不引入帧历史缓冲（显示尺寸下每帧约 7 MB，不划算）
- 不改变播放态的解码行为（背压只在暂停时生效）
