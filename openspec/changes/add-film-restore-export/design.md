## Context

`Exporter` 目前是一条**分享导向**的路径：单次 ffmpeg 子进程、单条 `-vf`、只允许缩小、
`-maxrate` 硬上限。它对「把 4K 大文件压成能发微信的体积」是合适的，但对老片是**反向**的。

目标素材：**DVD 压制的老片为主**（也需容纳录像带转录、旧数字存档）。这类素材的问题谱系与
现代压缩视频几乎不重叠：

```
现代压缩视频                老片（胶片 / 磁带 / 旧数字档）
─────────────────           ──────────────────────────────────
块效应、蚊噪、振铃           基本没有
                           隔行扫描 / 3:2 pulldown 梳状纹   ← 头号问题
                                 （用户常描述为"锯齿 / 马赛克"）
                           抖动（手持 / 放映机 / 转录）
                           胶片颗粒                        ← 是细节，不是噪声
                           褪色、对比度衰减、软
                           低分辨率（DVD 720×576 / VHS 352×288）
```

**已实测确认的环境事实**（决定了技术选型，避免纸上谈兵）：

| 事实 | 结论 |
|---|---|
| 随包 ffmpeg 9.0.2 已含 `fieldmatch` `decimate` `pullup` `detelecine` `bwdif` `yadif` `estdif` `idet` `vidstabdetect` `vidstabtransform` `bitplanenoise` `cropdetect` `removegrain` `chromanr` `noise` `curves` `eq` `colorlevels` `cas` | **本变更无需任何新依赖** ✓ |
| 随包 ffmpeg 含 `psnr` `ssim` `vif` `xpsnr` | 修复结果可**客观验证** ✓ |
| 本机为 Intel Iris Xe 核显；`libplacebo`（Vulkan）实测失败：`No memory type found for flags 0x2` | **不依赖 GPU 滤镜**，走 CPU swscale；GPU 加速只作为可选快路径 |
| `nnedi` 需要 `nnedi3_weights.bin`（本机不存在） | 默认用 `bwdif`；`nnedi` 作为可选（需 +1MB 数据文件） |
| 主 `openspec/specs/` 为空，`add-video-export` 尚未归档 | 本变更对导出行为的两处修改以新能力形式承载（见 proposal） |

## Goals / Non-Goals

**Goals:**

- 让 DVD / 老片经修复后**明显更清晰**：梳状纹消失、抖动减轻、可放大、胶片颗粒被保留
- 决策过程**可测**：由诊断与意图推导阶段清单是纯函数，可在无 GPU、无子进程的前提下验证
- 执行过程**可验证**：几何、帧数、指标可自动断言
- **不引入新依赖**（可选的 `nnedi3_weights.bin` 除外），发布包体积基本不变
- 建立**阶段化流水线骨架**，使后续 AI 超分作为「一个阶段」接入而无需重构

**Non-Goals:**

- AI 超分与机器能力探测 —— 属于 `add-ai-upscale`
- 划痕、脏点、闪烁的逐帧修复 —— ffmpeg 无此能力，需要专业工具
- 局部遮罩 / 逐帧手工干预、音频修复、批量队列
- 自动判断「该不该修」并**代替用户**决定 —— 见决策 D7
- 面部修复、色彩分级等超出「清晰度」范畴的加工

## Decisions

### D1：改造为「阶段化流水线」，而不是继续用单条滤镜链

| | A. 继续单条 `-vf` 链 | **B. 阶段化流水线（选定）** |
|---|---|---|
| v1（纯 ffmpeg） | 够用 | 够用 |
| `vidstab` 需要**两遍** + 中间文件 | 表达不了 ✗ | 天然容纳 ✓ |
| 预览一帧（截断到单帧） | 要从链里手工剥离 ✗ | 按阶段裁剪 ✓ |
| 后续 AI 超分（外部进程） | **必须重构** ✗✗ | 加一个阶段 ✓ |
| 进度语义 | 单一 out_time | 分阶段 + 加权 ✓ |
| 复杂度 | 低 | 中（阶段模型 + 进度合成 + 清理） |

选定 B。理由是**重构成本不对称**：现在建骨架很便宜，将来从单链改成阶段化很贵，
而 AI 超分是已确认的下一件事。

### D2：诊断与决策分离，决策做成纯函数

```
  源 ──▶ [诊断：子进程 + 解析] ──▶ 诊断结论（结构化） ──┐
                                                      ├─▶ [决策：纯函数] ──▶ 阶段清单
       用户意图（强度 / 目标分辨率 / 时间段）───────────┘
```

决策是 `(诊断结论, 意图) -> 阶段清单`，**不碰文件、不起进程**。因此：

- 可以用一个测试穷举各种诊断组合，断言阶段清单正确（无 GPU、秒级）✓
- 阶段清单可以**展示给用户**（"将要执行：去隔行 → 轻降噪 → 放大 2× → 锐化"），
  把一个黑盒变成可解释的过程 ✓

这也延续了项目既有做法：`Exporter` 的 `scaleFilter()` / `buildArgs()` 都是纯静态函数，
由 `export_check` 做 headless 断言。

### D2b：构造方自己校验顺序约束（实施时补充）

`buildPlan` 在返回前**自己检查**自己产出的阶段顺序，违反则把清单标记为
`valid = false`（调用方必须拒绝执行），而不是"尽力而为地跑"。

这么做是因为顺序约束的破坏后果是不可逆的：`反胶转/去隔行` 排到 `放大` 之后，
梳状纹会被放大成永久伪影，事后无法修复。让构造方自检 + headless 穷举断言
（扫描方式 × 强度 × 目标尺寸 = 80 种组合），可以把这类错误挡在构建期而不是
等到用户导出一段已经毁掉的视频之后。

### D3：默认走 CPU swscale，不依赖 GPU 滤镜

本机实测 `libplacebo`（GPU 高质量放大核 + 内置 deband）**不可用**：
`No memory type found for flags 0x2`（ffmpeg 的 Vulkan 内存分配在该驱动上失败，驱动版本 31.0.101.3358）。

因此放大采用 `scale` + `flags=lanczos`（默认）或 `spline`。不选 `xbr`/`hqx`/`epx`：
它们是**像素画/动画硬边**算法，作用在实拍老片上会产生油画感 ✗。

GPU 路径（`scale_d3d11` / `scale_vulkan` / `vpp_qsv`）作为**可选加速**保留，但 MUST NOT
成为正确性前提——本机已证明 GPU 路径会失败。

### D4：反胶转与去隔行必须早于放大（硬规则）

```
正确：  去隔行/反胶转 ──▶ 稳定 ──▶ 降噪 ──▶ 放大 ──▶ 加回颗粒 ──▶ 锐化 ──▶ 编码
错误：  放大 ──▶ ... ──▶ 去隔行          ✗ 梳状纹已被放大固化，去不掉
```

交错帧的梳齿在放大算法看来就是**高频边缘**，会被忠实地放大、加粗，变成永久伪影 ✗
这条规则在规格里被写成了可断言的需求（`REQ: 反胶转与去隔行必须早于放大`），
并且决策函数在构造出反序清单时应**拒绝执行**。

细分选择：

| 情况 | 处理 |
|---|---|
| 检出 3:2 pulldown（DVD 电影/美剧常见） | `fieldmatch` + `decimate`（还原原始 24p，**帧数减少是正确的**） |
| 纯交错（PAL 576i / 电视台录像） | `bwdif`（内置、无数据文件、质量好）；可选 `nnedi` 更优但需权重文件 |
| 逐行 | 不加任何去隔行阶段 |

### D5：保颗粒策略 —— 胶片颗粒是质感，不是噪声

`hqdn3d` 强档或 `nlmeans` 会把老片洗成"塑料蜡像" ✗，而且 AI 超分本身也倾向磨平颗粒 ✗
两者叠加会让老片失去胶片感。因此：

- 降噪**默认最轻**；保颗粒策略下施加强度上限（规格中已断言）
- 提供只作用于**色度**的降噪（`chromanr`）——老片常见彩色噪点而亮度颗粒要留
- 收尾可选**加回颗粒**（`noise` 滤镜）并配合编码 `-tune grain`

### D6：保真档的编码参数

```
-c:v libx265 -crf 16~18 -preset slow -pix_fmt yuv420p10le -tune grain
（不设 -maxrate；让 CRF 决定码率 —— 这是对原 design D3 的修改）
```

- **10bit 的兼容性取舍**：Hi10P 的 H.264 兼容性差 ✗，故保真档搭配 **HEVC 10bit**（兼容性更好）
- 必须提供**兼容模式**（H.264 8bit）供老设备/不支持 HEVC 的目标使用 ✓
- `preset slow` 比现有 `veryfast` 慢 3~5 倍；修复路径本来就要等待，可接受，
  但**必须给出预估耗时**并在界面展示

### D7：增强不自动应用，但主动给建议

对高质量源做修复 = 破坏 ✗。因此：

- 默认导出（分享类预设）**不含**任何修复阶段（规格中已断言）
- 诊断发现问题时，界面**提示建议**（"检出交错，建议开启去隔行"），但不代选
- 提供**预览一帧**，让用户在花时间前看见结果——"清晰"没有客观标准，
  唯一可靠的验收是用户看一眼

### D8：进度用「实测耗时比例」自校正，而不是等权

三阶段耗时差异可达 10 倍以上，等权会让进度条先冲一半再长时间停滞 ✗。

方案：初始权重取经验值；**每完成一个阶段，用该阶段实际耗时重算剩余阶段的权重**。
简单、自校正，且不需要先跑一段样本测量（那会增加启动延迟和复杂度）。

### D9：预览一帧跳过稳定阶段

`vidstab` 是两遍（探测全片 + 应用），单帧预览无法执行 ✗。因此：

- 预览跳过稳定阶段，并在界面**明确标注**「预览不含稳定效果」
- 其余阶段（去隔行、降噪、放大、锐化、色彩）全部参与预览

半成品预览但如实标注，优于为了"完整"而让预览等待数分钟 ✗

### D10：时间段导出的两个坑

1. **定位方式**：用 `-ss <起> -i <源> -t <时长>`（前置 `-ss`）。ffmpeg 会解码到目标点后
   才开始输出，结果是**帧精确**的，且不必从头解码全部内容。
2. **时域滤波的预热**：去隔行、降噪、去块都是时域相关的，片段开头几帧会因为缺少前序
   上下文而不稳定 ✗。因此需要在起止点**之前多解码一小段作为预热**（丢弃其输出）。

第 2 点是实测才会暴露的坑，规格里以「时间段与修复共存时结果与整段导出同位置一致」断言。

### D11：诊断的实现方式与降级

统一模式：`子进程 + 解析 stderr/输出文件 + 超时 + 失败降级为「未知」`。

| 诊断项 | 手段 |
|---|---|
| 交错 / 场序 | `idet` 的统计输出 |
| 3:2 pulldown | `fieldmatch` 匹配率 / `idet` 的重复场特征 |
| 噪点强度 | `bitplanenoise` 数值 |
| 抖动 | `vidstabdetect` 的结果文件中的位移统计 |
| 黑边 | `cropdetect` 的建议裁剪值 |
| 亮度 / 色彩 | `signalstats` 的均值与分布 |

- **采样范围**：不做全片分析（太慢），采用**均匀多段采样**（而非只看开头——
  老片的问题可能只出现在中段）
- **失败降级**：任一诊断项失败即标记「未知」并继续，绝不因单项失败中断整个诊断
- **逃生门**：提供手动指定扫描方式（交错/逐行）的入口，覆盖误判 ✓

### D12：不引入新依赖

全部使用随包 ffmpeg 已有滤镜。唯一可选新增是 `nnedi3_weights.bin`（约 1MB，用于更高质量的
去隔行）。因此本变更**不改变发布包体积量级**，也不引入任何新的许可证问题 ✓

## Risks / Trade-offs

- **[修复档耗时远超分享档]**（`preset slow` + 10bit + `vidstab` 两遍）→ 导出前给出预估耗时与阶段进度；支持只导出选中时间段，让用户先做短片
- **[过度处理反而比源更差]** → 不自动应用（D7）+ 预览一帧 + 保颗粒上限（D5）+ 诊断只做建议
- **[诊断误判]**（交错/pulldown 判断错）→ 单点失败降级为「未知」（不以「正常」代替）+ 手动指定扫描方式的逃生门（D11）
- **[时域滤波在片段开头不稳定]** → 起止点前的预热段（D10）
- **[`vidstab` 中间文件在崩溃后残留]** → 临时产物纳入启动清扫，与既有 `discardPartialOutput` 同源
- **[10bit 编码在旧设备上不能播放]** → 保真档默认 HEVC 10bit，并提供 H.264 8bit 兼容模式（D6）
- **[反胶转让帧数下降引起困惑]**（30 → 24fps）→ 界面明确说明这是正确结果，不是丢帧
- **[修复与播放争抢 CPU]** → 沿用既有「限制编码线程数」的做法，并为诊断/修复阶段分别标定
- **[GPU 路径不可用]**（本机实测 `libplacebo` 失败）→ 正确性不依赖 GPU，GPU 仅作可选加速（D3）

## Migration Plan

1. **诊断先行**：实现诊断子进程与解析（可独立验证，不依赖导出改动）
2. **纯逻辑**：实现阶段模型与「诊断 + 意图 → 阶段清单」的组装，配 headless 断言
3. **执行器**：阶段进度合成、动态权重、取消与临时产物清理
4. **界面**：新增「提升清晰度」档、强度选择、时间段、预览按钮、诊断摘要与建议
5. **回归**：既有分享类预设的**行为必须完全不变**（参数、输出命名、进度语义）

**回滚**：修复能力与既有分享路径并行存在，回滚只需移除新增档位与源文件，
不影响既有导出能力（与 `add-video-export` 的回滚性质一致）。

## Open Questions

- 保真档默认编码取向：HEVC 10bit（质量优先）还是 H.264 8bit（兼容优先）？
- 诊断采样：均匀多段采样的段数与每段时长如何标定（需实测在不同素材上的命中率）
- 是否需要「修复后与源并排对比」的导出结果预览，而不只是单帧预览？
- 修复档是否要单独的线程数限制（避免边修边播时播放卡顿）——需实测标定
- `nnedi3_weights.bin` 是否随包（+1MB 换取更优去隔行质量）？
