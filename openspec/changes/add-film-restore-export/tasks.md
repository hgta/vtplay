## 1b. 实施记录（任务组 1 的实测结论与偏差）

- [x] 1b.1 **`bitplanenoise` 不可用，噪点改用代理指标**：它与文档描述不同，
      **不往 stderr 写数值**（实测 info / verbose / debug / trace 四个等级都取不到），
      画面则原样透传（与裸 `signalstats` 输出逐字节相同，已对照验证）。
      改用 `gblur` 差分残差 + `signalstats` 读高频能量。
      **代价**：该指标同时包含真实纹理与噪点，无法分离，因此只用于分级与纵向比较。
- [x] 1b.2 **`vidstabdetect` 必须用相对路径 + 工作目录**：把 Windows 绝对路径写进
      滤镜串（`result=D:/...`）会被 ffmpeg 滤镜语法解析器炸掉
      （实测 `Error parsing a filter description`）。相对路径 + `QProcess` 工作目录可完全绕开。
- [x] 1b.3 **抖动指标用「全局位移的二阶差分」**而不是位移大小：平滑摇镜的二阶差分≈0，
      抖动才是位移的高频分量。已用断言验证：位移总量相同（55 像素）时，
      摇镜得 0、来回抖动得 20 —— 证明指标衡量的是正确的东西。
- [x] 1b.4 **pulldown 必须在判据里先于「纯交错」**：3:2 pulldown 的梳状帧同时表现为
      「交错」与「重复场」，两者的正确处理方式不同（反胶转 vs 去隔行），混淆会毁掉输出。
- [x] 1b.5 **黑边结论必须是三态**：拿不到源尺寸时判为「未知」而不是「无」——
      早期版本用 `bool` 导致静默报「无」，等于宣称"已确认没有黑边"。已改为 `DiagLevel`。
- [x] 1b.6 **诊断必须无条件限时（`-t`）**：早期写成"已知总时长才加 `-t`"，
      结果不知道时长时每个探针都跑完整个文件——实测 1.5 分钟素材耗时 80 秒，
      换两小时老片就是十几分钟。修正后同一素材降到 36.9 秒。
- [x] 1b.7 **超时有重入陷阱**：`kill()` 会让 `finished` 信号**同步**触发，
      超时处理与被中断的处理会各推进一步（诊断"双跳"跳过一项）。用 `stepTimedOut_` 标志隔离。
- [x] 1b.8 **子进程启动失败/FailedToStart 的显示陷阱**：工具退出码 `-1073741515`
      （`STATUS_DLL_NOT_FOUND`）时 PowerShell 不会报错、只是没有输出——
      排查时容易被误认为"程序跑了但没输出"。
- [ ] 1b.9 **已知性能问题（未解决）**：5 个探针 × N 段 = 15 次 ffmpeg 启动，
      每次约 1~2 秒启动开销，是耗时主因。曾考虑把只读类滤镜（`idet`/`cropdetect`/
      `signalstats`）串成一条链以减半启动次数，但**这与规格里「单项失败只降级该项」
      的隔离要求冲突**（一条链里任一滤镜出错会带走三项），故暂不做。
      若要优化，应走「分段并行」而不是「滤镜串联」。
- [ ] 1b.10 缓存目前是**进程内**的（`QHash`，指纹 = 路径+大小+修改时间）。
      规格只要求"重复诊断不重复计算"，未要求跨进程持久化；跨进程持久化留待需要时再做。
- [ ] 1b.11 取消（1.10）已实现但**未做实测**：需要一次足够长的诊断才能可靠触发，
      留到与界面接入一起验证（那时有真实的老片素材）。
- [x] 1.13 headless 验证：对**人工构造**的已知素材断言诊断结论
      （交错素材 → 检出交错；逐行素材 → 不误判；含 pulldown 素材 → 检出 pulldown）

## 4b. 任务组 4 的增量说明（执行器拆成两段做的原因）

任务组 4 被拆成「执行计划（纯逻辑）」与「进程编排」两段。**先做的是纯逻辑那一段**，
因为其中的判断最容易在实现时被"顺手"写错，而且写错后很难从现象倒推原因：

- [x] 4b.1 **预热段**（`prerollSeconds`）：去隔行/降噪/稳定都是时域滤波，
      片段开头缺少前序上下文会不稳定。**只有时域滤波需要预热**，
      纯空间滤波（缩放/锐化/色彩）不需要——这一条已用断言区分开。
      具体秒数是经验值，需用真实素材标定。
- [x] 4b.2 **进度权重自校正**（`reweightStages`）：初值只是起点，
      完成一个阶段后按**实测耗时**换算速率并重估剩余阶段。
      ⚠️ 需要说清它的作用边界：它纠正的是**预计剩余时间**，
      不改变进度条在各阶段之间的分配比例（比例由权重之比决定，单样本无法校正）。
      规格里"长阶段不会让总进度长时间停滞"靠的是初值比例合理，不是靠这一步。
- [x] 4b.3 **预览跳过稳定**（`previewPlan`）：稳定是两遍全片 + 中间文件，单帧无法执行。
      选择"半成品预览 + 如实标注"而不是"让预览等几分钟"。
- [x] 4b.4 **临时空间估算**集中在 `estimateTempBytes`：当前只有稳定阶段消费它，
      但集中在一处是为将来 AI 超分的帧序留接口（那才是真正的磁盘大户）。
- [ ] 4b.5 **尚未实现（进程编排）**：阶段执行循环（4.1）、阶段进度（4.2）、
      把 `-ss/-t` 与预热真正拼进参数（4.5 的后半）、临时目录管理（4.7）、

## 4c. 端到端打通后的两个待修问题（首次真机跑出来的）

第一次完整导出已经跑通（`vtplay-diagnose-check <src> --restore <out>`：诊断 → 决策 →
执行 → 产物），产物的**分辨率、10bit 编码、临时目录清理**都正确，
但暴露两个必须修的问题：

- [x] 4c.1c **★ 根因确定：时间范围只裁了视频，没裁音频**

      最后一个实验把假设空间砍半：**用执行器的完整参数原样跑一遍，
      只把编码器换成 libx264** → 仍然是 `Duration 15.17` ✗
      （与之前成功的对照实验的唯一区别是：成功的那个加了 `-an`）

      **根因**：`-vf` 只作用于视频流，音频**原样穿过**。
      于是产物里是「2 秒的视频 + 15 秒的音频」，
      容器 Duration 取两者最大值 → 15.17 秒 ✗

      这一条解释了此前所有看似矛盾的现象：
        · 视频帧数正确（120）✓ —— 视频确实被 trim 裁了
        · 容器 Duration 却错 ✗ —— 音频没裁，主导了时长
        · 去掉音频的对照实验完美 ✓ —— 没有音频就没有这个矛盾
        · 换编码器无效 ✗ —— 与编码器无关
        · r6/r7 字节数完全相同 ✗ —— 音频完全一致，
          视频 PTS 的差异被容器时长掩盖（也说明 setpts 的修改其实生效了，
          只是从 Duration 上看不出来）

      **修法**：让音视频**对称**地应用同一个时间范围——
        视频：`-ss (start-prewarm)` + `trim=start=P:end=END`
        音频：同样的 `-ss` + `-af "atrim=start=P:end=END,asetpts=N/SR/TB"`
      用 `atrim`/`asetpts` 与视频的 `trim`/`setpts` 一一对应，
      两者都按帧/采样序号重建时间戳，避免再出现"一边归零一边不归零"。

      **验证方式**：断言产物 `frame` 数 == 期望帧数 **且** `Duration` == 期望时长
      **且** 音频流时长 == 视频流时长（三条都要，前两条这次都骗过了我）。

- [x] 4c.1b **（历史记录）曾收窄到"调用方式或编码参数"**

      决定性对照实验：**同样的滤镜链 + `setpts=N/FRAME_RATE/TB`，
      直接命令行编码成 mp4 → `Duration 00:00:02.00` ✓✓（frame=120 ✓）**
      说明链本身完全正确 ✓

      但经执行器跑出来的 r7.mp4 与修复前的 r6.mp4 **字节数完全相同**
      （14048903），即新 setpts 在真实运行里同样没有生效 ✗。
      同一串参数、两种结果 → 差异只可能在**调用方式**或**编码参数**上。

      直接实验用的是 `-c:v libx264 -crf 28`；
      执行器用的是 `libx265 -preset slow -crf 20 -pix_fmt yuv420p10le -tune grain`
      + `-movflags +faststart` + `-progress pipe:1` + 工作目录设置。

      **下一步的收窄办法**（按差异逐项排除，每次只改一项）：
        1. 用执行器的方式（QProcess + 完整参数）跑一次**不带 filter** 的时间段导出，
           看时间戳是否正确 → 判断是 QProcess 传参问题还是编码参数问题
        2. 把执行器的编码参数逐项换成直接实验的（先换 libx264）
        3. 去掉 `-movflags +faststart` 单独测一次（faststart 会重写文件）
      每一步都用「**帧数 + Duration 双查**」判断，别只看其中一个。

- [x] 4c.1 **时间段：内容对了，时间戳错了**（历史记录，保留以便追溯）

      证据链（三条，缺一不可）：
      1. 加了 `commandBuilt` 信号后拿到**实际命令行**，参数拼接正确：
         `-ss 4.500 -i <src> -vf hqdn3d=…,noise=…,trim=start=0.500:end=2.500,setpts=PTS-STARTPTS`
      2. 把这条链**原样单独跑**（含 hqdn3d / noise / trim / setpts 的全部组合）：
         全部得到 `time=00:00:02.00` ✓ —— 滤镜链本身没问题
      3. 解码产物 r6.mp4：**`frame=120`**（2 秒 × 60fps，内容完全正确 ✓）
         但 `time=00:00:15.16`、`Duration 15.17` ✗

      **结论**：trim 生效了、帧数正确，错的是**时间戳**——
      120 帧的 PTS 仍横跨 `4.5 → 19.67`（正好 15.17 秒），
      即 `setpts=PTS-STARTPTS` 没有把它们归零。
      影响：播放器会认为这是 15 秒的视频（内容挤在开头 2 秒），
      拖动进度条、时长显示、二次转码都会错。

      **候选修法**：把 `setpts=PTS-STARTPTS` 换成按帧序号重建时间戳的
      `setpts=N/FRAME_RATE/TB`——它不依赖输入时间戳，直接由帧序号与帧率算出
      PTS，因此对 `-ss` 输入定位造成的偏移免疫。
      **验证方式**：修完后断言「产物 `frame` 数 == 期望帧数」**且** `Duration` 相符
      （只查帧数会漏掉这个 bug —— 这次就是只查 Duration 才误判成"裁剪没生效"）。
      教训：**长度类的结论必须同时看帧数与时间戳**。
- [ ] 4c.2 **主遍的阶段名是错的**：主遍把**整条滤镜链**一次跑完，
      但代码按 `stageIndex` 固定显示"降噪"，整个主遍都在报这一个阶段 ✗
      正确做法：主遍内按 `reweightStages` 得到的权重比例，
      用进度位置**反推**当前在做哪一段，名字随进度推进。
      这正是权重该被用到的位置（当前权重只用在 ETA 上）。
- [ ] 4c.3 **默认阈值偏激进**：该素材抖动只是"轻度(1.23)"却被加入了稳定阶段
      （规则是 `Mild && strength >= Medium`），于是额外跑了一整遍探测，
      导出速度掉到 0.1x。稳定是两遍全片处理，代价很高，
      默认是否只对 `Obvious` 自动启用、`Mild` 只在"强力"档启用，需要按真实老片标定。
- [ ] 4c.4 保真档体积需要看一眼：4 秒 1080×1920 的 10bit x265 + crf 20 得到约 100MB
      （约 51 Mbps）。对"保真"而言可能是合理的，但要确认这不是参数写错导致。

## 5n. 修复导出期间界面停在 idle（真机复现 → 已修 → 已验）

**现象**：点「按此方案导出」后 ffmpeg **确实在跑**（控制台有
`[restore] main: ffmpeg ... hqdn3d=... noise=... libx265` 那行命令），
但对话框**切不到「正在导出…」**：没有阶段行、没有进度、**底部也没有取消按钮**——
看上去就是"点了没反应"，而且任务跑完前无法中止。

**根因：5f.3 只修了一半。** 5f.3 把 `dlg.phase` 的驱动改成 `player.exportRunning`
（方向正确），但 `exportRunning()` 本身只看**分享导出**的执行器：

```cpp
return exporter_ && exporter_->isRunning();   // 修复导出走的是 restoreRunner_
```

修复导出用的是**另一个执行器** `restoreRunner_`，于是它运行期间
`exportRunning()` 恒为 `false` → `phase` 停在 `idle` → 「导出中」整段（阶段行在其中）
与取消按钮都不满足 `visible` 条件。
**教训**：5f.3 把状态源换成了一个**聚合视图**，却没检查该视图是否聚合了全部执行器。
"单点真相"只有在真的覆盖全部路径时才是真相。

**修复（三处）**：
1. `PlayerController::exportRunning()` 同时计入 `restoreRunner_`
   —— `(exporter_ && ...) || (restoreRunner_ && ...)`。
2. `PlayerController::cancelExport()` 同时取消 `restoreRunner_`
   —— 这是**第二个独立缺陷**：否则取消按钮即使出现也按不动修复导出，任务仍会跑完。
3. `ExportDialog::resetForm()` 不再无条件置 `phase = "idle"`，改为按
   `player.exportRunning` 判定。原因：`exportStateChanged` **只在执行器起/停时发一次**，
   进度刷新不重发；导出中途关掉对话框再打开时，`onOpened → resetForm()` 会把它压回
   `idle`，且**再没有任何信号会纠正它**，顺带还会放出「开始导出」让用户叠第二路 ffmpeg。

**验证**：编译 + 链接通过、`read_lints` 无新增诊断；**用户实跑确认功能正常**
（对话框进入「正在导出…」、阶段行与取消按钮出现）。本次不需要夹具，
由人工触发复验即收口了 5f.5 / 5m / 5l.4 / 5k 四处欠账。

## 5m. 找到并修掉「静默失败」——导出被无声丢掉

**现象**（自动夹具实测）：`startRestoreExport` 被调用、无报错，
但 `exportRunning` 始终为 false，之后**既无进度也无完成/失败** ——
导出**静默地什么也没做**。

**根因**（`RestoreRunner.cpp:121`）：
```cpp
if (d_->running) return;      // 静默返回，不报任何错
```
`d_->running` 是个**残留标志**时，后续导出就在这里被丢掉，且不给任何提示。

**为什么上一轮成功、这一轮失败**（这个对比是关键证据）：
上一轮**预览是失败的**（那时还没修时间点越界），没走到会留下标志的路径；
这一轮预览**成功了**（clamp 修复生效）→ 标志残留 → 导出被吞。
**即：修的 bug 暴露出了另一个潜藏的 bug。**

**修复**（两处，缺一不可）：
1. 只有**真的还有子进程在跑**才算忙；否则复位残留标志并继续执行。
   这样"标志卡住"再也不会永久堵死这个功能。
2. 真忙时改用 `failWith(...)` **明确报错**，而不是静默返回——
   静默返回是这次最难排查的原因：日志干净、界面正常、就是不动。

**已删除临时夹具**（`RestoreOptions.qml` 55 行），构建通过、零残留。

## 5k. 5j 两处结论（一处我判错了）+ 一个更根本的设计限制

**5j.2 —— 不是 bug，是刻意的设计（我上一轮判断错了）**：
```cpp
enc.tenBit = (intent.strength != RestoreStrength::None) && !intent.preferCompatibility;
```
`strength == None` 时**固定 8bit**，是有意为之。但由此暴露出一个**真实的界面/行为不一致**：
界面写着"质量优先 HEVC 10bit"，实际给的却是 8bit。
**已修**：强度为「不处理」时禁用两个编码取向按钮，并在下方标注原因
（"按兼容档输出 H.264 8bit，编码取向不生效"）。
控件不能承诺它做不到的事——这属于诚实性修复，不是功能变更。

**5j.1 —— 索引语义确实错位，但成因比我说的更根本**：
`d_->stageIndex` 是**遍数**索引（0=探测遍 / 1=主遍），不是阶段索引。
**已修（保守）**：夹进合法范围后取阶段名，**保证不返回空串**。
理由：空串会让界面那行完全不显示，用户失去唯一的过程信息。

**更根本的限制（值得记住）**：所有修复阶段是串在**同一条 ffmpeg 滤镜链、一次主遍**
里完成的（这是刻意的效率选择，见 `RestoreRunner` 的说明）。
因此主遍**根本不存在"阶段边界"**——精确的"当前阶段"在原理上就拿不到，
只能由总进度近似推断。
→ 所以界面**不该声称"当前阶段是 X"**；更诚实的做法是显示
**完整方案**（"将执行：去隔行 → 降噪 → 放大 → 编码"）配总进度。
阶段名只作为粗略提示。**这一条应反映到界面上**（未做）。
